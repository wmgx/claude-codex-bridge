# Claude 与 Codex 协作规范

用户决定产品目标、范围和需要授权的操作。Claude 把目标写成规格，负责验收并向用户交代结果。Codex 在约定范围内决定实现方式，负责实施、实测和提供证据。

## Claude 怎样派单

Codex 适合按具体规格独立执行。按以下顺序写每轮方案，让它知道可以自己决定什么，也知道要留下什么供你验收。

1. **约束**。先写本轮适用的限制，例如“不提交、提示用 Toast、单文件最多 800 行、不做旧版兼容”。只读任务写明“只读，不要改文件”。删除、强推、发布、对外发送等不可逆操作不要在方案里授权。
2. **分项需求**。写清入口、用户操作和预期结果。外观、交互、颜色按规格实现。规格未写的细节只照搬项目现有同类组件，尽量指明参照物，例如快捷面板里的卡片、胶囊按钮或现有轻提示。不要自创新样式、颜色、动画或图标。
3. **同类问题排查**。圈定要检查的同类对象和检查项。例如修面板返回时，逐个核对相关面板从哪里打开、点返回后到哪里，把例外列出来。
4. **验收标准**。能量化的写明操作、测量口径和阈值，例如“从点击到面板首次可见 ≤ 2 帧”或“指定样本中行首违规数 = 0”。交回时逐项给实测值、测量环境及可复核的录屏、日志或命令输出。
5. **结束状态**。用到模拟器时，写清验收后要恢复的数据、页面和位置，方便用户接手复查。

派单时写明：“做完再汇报。范围内可逆的实现细节自己拿主意，交回时写明取舍。”规格相互冲突、找不到可照搬的组件或需要扩大范围时，先做完不受影响的部分，再把待决定的问题交回。需要用户批准的操作，交由用户决定。

每轮已定方案开新线程，把本轮需要的规格、参照和验收条件带齐。答疑、补证和返工留在本轮线程。独立工作可以并行。先分清文件归属，同一文件同一时间只由一方修改。耗时测量放后台跑，等待时可以读 diff、核对文案；测量期间让执行方独占模拟器。

## Codex 怎样交回

按派单顺序逐项写“目标 → 实测结果 → 证据位置”，让 Claude 能直接找到对应的截图、录屏、日志或 diff。再列出同类排查的结果、复用的组件、实现取舍、规格偏差和未验证项。用到模拟器时写明最后停在哪里。

## Claude 怎样验收

收到交回结果后，Claude 按派单标准逐项验收。Codex 的汇报用来定位证据。

- 功能和性能改动要读 diff，核对测试输出或测量记录，必要时重跑。原问题未复现时，写清试过的路径、次数和观察结果，把推测的根因标为推测。
- 视觉和交互改动要亲自打开本轮截图或录屏，对照规格检查各状态、对齐和返回去向。让 Codex 逐项列出照搬的组件及其来源，以及与规格的每一处出入。
- 提示类改动要求列出本轮排查中新增、修改和保留的完整文案。逐句读，核对触发条件和计数含义，例如全部失败时，“已检查”和“失败”各指哪些对象。
- 向用户交回已核实的结果、实现取舍、规格偏差和未验证项。涉及模拟器时，核对约定的结束状态。

证据缺失或结果偏离规格时，Claude 在原线程指出具体条目、实际表现和预期结果，要求补证或返工。再次交回后复核该项和受它影响的路径。需要用户判断的视觉取舍，附上对应截图和待决定的差异。
